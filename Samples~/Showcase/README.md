# BRIO: FIRST HARMONIC – an SFX FORGE showcase

A one-level 2D momentum platformer in which **every sound is SFX FORGE at runtime**: 19 sound effects
synthesized from patches written in code, and a song whose layers follow the player's speed. There is
no audio file, texture, model or font anywhere in this folder – the art is generated meshes, the
scene is generated by an editor script.

It exists to be read and copied. The game is small on purpose; the part to take home is
[`Scripts/Audio`](Scripts/Audio), seventeen short files that show the three ways to use SFX FORGE in a
Unity game: **one-shots**, **sounds that follow the game while they play**, and **adaptive music**.

**The Unity manual**, [`Documentation~/UNITY.md`](../../Documentation~/UNITY.md), explains the package itself – every value of a
patch, the three routes, the music player, the link to the device – and uses this game as its worked example.

Brio is an original character and First Harmonic an original level: running builds speed, slopes and
loops carry it, a Tuck rolls, a Wind-Up charges a Burst, Woofers throw you, Chimes are collected and
scatter when you are hit, Tuning Forks are checkpoints and the Resonator is the goal.

> folder and press Play. The page below was written in the repository the package is generated from: where
> it says `unity/Demo`, read "your project"; where it names `docs/`, `tests/`, `videos/`, `out/` or `.tools/`, those are
> that repository's and are not in the package (the videos and figures are made there). The older demo it

> folder or repository, not from the imported copy under `Assets`. The tests in `Tests/` are compiled
> only when the Test Framework package (`com.unity.test-framework`) is in the project, and a new project

1. Open the Unity project `unity/Demo` (Unity 6000.3.8f1).
2. Open the scene `Assets/Showcase/Showcase.unity` and press Play.

**In another place.** This page names paths as they are in the SFX FORGE repository, where the folder is
`unity/Demo/Assets/Showcase`. Imported as the package's sample it is
`Assets/Samples/SFX Forge/<version>/Showcase` of your own project, and it may be moved anywhere under `Assets`:

`unity/Demo` as "your project". Two defaults differ outside the repository: a build goes to `Builds/Brio/` and
the capture rig records to `Captures/`, both in the project's folder beside `Assets`. The folder was checked in a
second place by copying it to `Assets/Elsewhere/Deeper/Showcase` of an otherwise empty project (the checks, the
tests, a build and its probe); importing it through the Package Manager's Samples list is the same copy, made by
Unity. What a new project does not have: the scene in its build settings. `Verify` says so in one failed check
until **SFX Forge > Rebuild Showcase Scene** has added it, or you have; playing, the tests and the build do not
need it.

| | Keyboard | Gamepad |
|---|---|---|
| Run | Left / Right or A / D | left stick |
| Jump (hold for a full jump, tap for a hop) | Space or Z | a face button |
| Tuck into a roll (while moving) | Down or S | stick down |

three warnings in the Console (one per kind of component: the effects, the players, the music). No
device and no MIDI connection are needed.

## Check it, test it, rebuild it

Nothing in `Showcase.unity` or `Generated/` is edited by hand: both are written by
`Editor/ShowcaseBuilder.cs`. Headless, from Git Bash (only one Unity process may have the project
open; each run takes one to three minutes):

```sh
UNITY="C:/Program Files/Unity/Hub/Editor/6000.3.8f1/Editor/Unity.exe"   # where your Unity 6000.3 is
PROJECT="$PWD/unity/Demo"                           # run from the repository's root
OUT="$PWD/out"

# CHECK: compile, open the saved scene, run the editor checks. Writes nothing.
"$UNITY" -batchmode -quit -projectPath "$PROJECT" -executeMethod SfxShowcase.Editor.ShowcaseBuilder.Verify -logFile "$OUT/unity-showcase.log"
grep "SHOWCASE:" "$OUT/unity-showcase.log"          # one "SHOWCASE: ok" line per check, then "SHOWCASE: PASSED"

# TEST: the play mode tests of Assets/Showcase/Tests and Assets/SfxDemo/Tests together
"$UNITY" -batchmode -projectPath "$PROJECT" -runTests -testPlatform PlayMode -testResults "$OUT/unity-showcase-playmode.xml" -logFile "$OUT/unity-showcase-playmode.log"
grep -o '<test-run [^>]*' "$OUT/unity-showcase-playmode.xml"
grep "SHOWCASE RUN" "$OUT/unity-showcase-playmode.log"   # where the test pilot was each second, and its launch speeds
```

Exit code 0 is success; compile errors appear in the log as `error CS`.

**Rebuild** after changing the level (`Scripts/Level/LevelLayout.cs`), the sounds
(`Scripts/Audio/SoundLibrary.cs`), the look (`Scripts/Art`) or any installer: in the editor
**SFX Forge > Rebuild Showcase Scene**, or headless

```sh
"$UNITY" -batchmode -quit -projectPath "$PROJECT" -executeMethod SfxShowcase.Editor.ShowcaseBuilder.SelfTest -logFile "$OUT/unity-showcase.log"
```

which rebuilds and then runs the same checks as `Verify`. A rebuild rewrites `Showcase.unity` and
`Generated/ShowcaseMeshes.asset` from top to bottom (a new scene gets new file IDs), so both files
show as changed in git even when nothing visible changed: rebuild when something changed, not to
check. It also makes sure the scene is in the build settings' scene list, the one thing the showcase
touches outside its own folder.

The original demo has its own check, `-executeMethod SfxDemo.Editor.SfxDemoBuilder.SelfTest`. It
regenerates the demo's scene and sets the build settings to that scene alone, so run it BEFORE the
showcase's `SelfTest` if you run both (the showcase's `Verify` checks that its scene is listed; the
PlayMode tests load it by path and do not depend on the list).

The PlayMode tests play the game through the same seam the keyboard uses
(`PlayerBase.InputOverride`, see `Tests/ScriptedInput.cs` and `Tests/RunPilot.cs`).
`ShowcaseTests.cs`: standing at the spawn, cruise speed, jump height, a steep slope carrying a player
who lets go, the Wind-Up and Burst, the hills and the first loop, turning round in a loop's switch, a
Woofer's flight, Chimes collected and scattered, respawns at a Tuning Fork and out of a pit, the low
route, the goal and a restart, and a whole run from start to goal that also measures the two launch
ramps. `ShowcaseAudioTests.cs`: a jump and a Chime are really heard through SFX FORGE, the Wind-Up
rev and the roll hum sound and bend while they play, Static Field's pattern is cued and held, and the
music's intensity follows speed and drops on a hit.

## A standalone build

The game as an executable, with no editor near it: Windows x64, this one scene.

```sh
"$UNITY" -batchmode -quit -projectPath "$PWD/unity/Demo" -executeMethod SfxShowcase.Editor.ShowcaseBuild.BuildWindows -logFile out/build.log
grep "SHOWCASE BUILD" out/build.log                 # SHOWCASE BUILD: ok .../out/build/Brio/Brio.exe (85 MB, ...)
```

In the editor: **SFX Forge > Showcase > Build for Windows**. The build goes to `out/build/Brio/` at the repository's
root, and in any other project to `Builds/Brio/` in the project's folder (another place: `-sfxforge-build <path to the .exe>`). The build settings and the project's settings are left
as they are.

The built game checks itself when it is asked to. Started like this it plays by itself for 14 seconds, measures what
comes out of its AudioListener, writes a report and a picture, and quits with exit code 0 or 1:

```sh
out/build/Brio/Brio.exe -screen-fullscreen 0 -screen-width 1280 -screen-height 720 -sfxforge-probe "C:\\somewhere\\probe.json"
```

`ok` in the report means: the native library was found, the title card was left, the song ran through at least two
bar lines, every baked sound has its clip, a jump happened, and the output was not silent for at least a quarter of
the frames. The report also has the patterns heard, the highest intensity, the output's peak and level and the
counts of jumps, landings, footsteps and Chimes ([`Scripts/Audio/BuildProbe.cs`](Scripts/Audio/BuildProbe.cs)).
Without the argument the probe does nothing.

What a pass does not tell you: how it sounds. The probe measures that sound comes out and that the song moves; it
does not compare the sound with the editor's, and nobody has listened to the build. It was run on one machine
(Windows 11, Unity 6000.3.8f1, Mono).

## Use SFX FORGE in your own Unity game

Each step names the file to read here. The files are short and commented for exactly this.

### 0. Install and make a seam

- Add the package (the package's README, "Install"), and reference `CatSplat.SfxForge`
  from the assembly your audio code lives in ([`SfxShowcase.Audio.asmdef`](Scripts/Audio/SfxShowcase.Audio.asmdef)).
- Give your game a place where it says what happened without knowing about sound:
  [`Scripts/Core/GameEvents.cs`](Scripts/Core/GameEvents.cs) is a static class of C# events
  (`Jumped`, `Landed(impactSpeed)`, `ChimeCollected(combo)` …). Gameplay raises them; the audio
  subscribes in `OnEnable` and unsubscribes in `OnDisable`. Anything continuous (speed, rolling) is not
  an event: the audio reads it every frame.

### 1. Write your sounds as patches – [`SoundLibrary.cs`](Scripts/Audio/SoundLibrary.cs)

A sound is an `SfxPatch`: an engine (`Impact`, `UiBlip`, `SciFiFm`, `Foley`, `Wavetable`) and up to 25
values in the order of the device's pages.

```csharp
// FREQ, PITCH ENV, ENV TIME, A, B, NOISE, CUTOFF, RESO, DECAY, CRUSH, then ATTACK, SUSTAIN, RELEASE …
SfxPatch coin = SfxPatch.Create(SfxEngine.UiBlip, 86, 64, 0, 26, 60, 0, 127, 0, 62, 0);
```

`SoundLibrary.cs` wraps that call in `Make(engine, frequency: …, decay: …)` so every number has a
name, keeps one commented patch per effect, and ends in one table: sound, patch, route, the MIDI note
it is tuned to, volume. The header comment explains each parameter; the device's manual (`Documentation~/MANUAL.md` in the package)
has the full reference, and the firmware's factory presets (`sfx-forge/fw_sounds.h`, `PRESETS`) are
good starting points. A bare `new SfxPatch()` has level 0 and is silent: always start from `Create`.

To keep a sound as an asset you can click and tune, put the patch in an `SfxPreset`
(`ScriptableObject`): the builder does that for every entry (`ShowcaseAudio.CreatePresetAsset` in `Editor`).
The preset's Inspector is the device's sound page: seven pages of four knobs with the values in the device's
units, the waveform, and keys to play, mutate and bake it (the Unity manual, "The inspectors look like the
device"). A rebuild writes these presets from `SoundLibrary.cs` again.

### 2. One-shots – [`SoundEffects.cs`](Scripts/Audio/SoundEffects.cs)

Two routes, chosen per sound in the library's table ([`SoundRoute.cs`](Scripts/Audio/SoundRoute.cs)):

- **Baked** – for short sounds that fire often and are always the same. Render the preset to an
  `AudioClip` once and play it like any clip:

  ```csharp
  AudioClip clip = preset.Bake(AudioSettings.outputSampleRate, midiNote: 76);   // in Awake; null without the native library
  oneShotSource.PlayOneShot(clip, volume);                                      // in the event handler
  ```

  See `BakeClips`, `PlayBaked`, and how a landing's volume follows its impact speed and the footsteps'
  pitch follows the running speed.
- **Live** – for a sound decided at the moment it plays. An `SfxPlayer` synthesizes it on the spot:

  ```csharp
  sfxPlayer.preset = chimePreset;
  sfxPlayer.Play(velocity, semitones, midiNote);     // each Chime of a combo one step up the scale
  ```

  See `OnChimeCollected` and `PlayScatter`. One `SfxPlayer` holds one patch, so live one-shots go
  through [`LiveVoicePool.cs`](Scripts/Audio/LiveVoicePool.cs): the voice already playing that preset,
  else a silent one, else the oldest.

### 3. Sounds that follow the game while they play – [`ContinuousSounds.cs`](Scripts/Audio/ContinuousSounds.cs)

What a synthesizer gives you that samples cannot. A held patch (SUSTAIN above 0) on an `SfxPlayer` of
its own; start it, then write its four live values every frame:

```csharp
rollHumPlayer.Play(1f, 0f, 40);                                    // hold, as the MIDI note E2   (HeldSound.Hold)
rollHumPlayer.pitchSemitones = speed01 * 12f;                      // 0..24
rollHumPlayer.cutoffOctaves = Mathf.Lerp(-1f, 1.5f, speed01);      // -4..4
rollHumPlayer.level = Mathf.Lerp(0.35f, 1f, speed01);              // 0..1
rollHumPlayer.Release();                                           // let go: it fades over the patch's RELEASE
```

Start a pitched held sound with its MIDI note like any other sound: a bare `Play()` sounds at the
patch's own FREQ, which is rarely in tune with anything (noise such as the wind has no note and is
started with 0). The player glides to each live value over 30 ms, so writing every frame does not click. The file has three
examples: the roll hum (pitch, filter and level from speed), the wind (level and band above 60 % of top
speed) and the Wind-Up rev (retriggered on each tap; pitch, `fm` and filter from the charge).
[`HeldSound.cs`](Scripts/Audio/HeldSound.cs) is the ten lines of hold / let go / retrigger.

### 4. Adaptive music – [`MusicDirector.cs`](Scripts/Audio/MusicDirector.cs)

An `SfxMusicPlayer` plays an `SfxSong` asset (16 sounds and a sequenced song, made on the device; the
package cannot write one, and its Inspector changes only the tempo, the swing and a sound's layer, volume and pan). The showcase plays its own `Song/DemoSong.asset`, the firmware's demo song; the
builder writes the asset from `Song/DemoSong.bytes`, the song as the device sent it. The
director turns the game into five calls:

```csharp
music.intensity = …;                        // 0..1, every frame: each instrument plays only at or above its layer mark
music.CuePattern(4);                        // another pattern of the song, from the next bar line (see below)
music.PlaySound(instrument, velocity, 76);  // a note by hand on one of the song's instruments, on top of the music
music.volume = …;                           // a dip when the player is hurt (not smoothed by the player: ramp it yourself)
music.Stop(); music.Reload(); music.Play(); // the song ends at the goal and starts again with a new run
```

Here the song plays as it was arranged – the demo song's sixteen bars, A B A B C D C D E E A B C D C F,
round and round – and the game decides how much of the band plays it. Each section of the level has a
floor ([`SectionCue.cs`](Scripts/Audio/SectionCue.cs)): the intensity when the player stands still,
0.42 to 0.60, which is the rhythm section (kick, hi-hat, bass, snare) and from the third section to the seventh
the strings. Speed fills the rest of the way to 1 in a straight line (rising in 0.6 s, falling in
2.5 s): the keys, then the brass, then the bells. Two places leave the song's order and hold one
pattern: Static Field holds E, the breakdown, while the player is in it, and the last launch holds F,
the turnaround, until the goal. A checkpoint is answered by three bell notes started on the song's
next sixteenth, and the goal stops the song and plays a fanfare by hand
([`MusicNote.cs`](Scripts/Audio/MusicNote.cs), [`MusicKit.cs`](Scripts/Audio/MusicKit.cs),
[`Pitch.cs`](Scripts/Audio/Pitch.cs)).

What `CuePattern` does depends on the song. A pattern that is not in the song's arrangement stays
until the next cue. So does any pattern in a song without an arrangement (`SfxSong.ArrangementBars`
is 0) whose chain is 1; with a longer chain the cued pattern plays one bar and the chain walks on. A
song WITH an arrangement – the demo song has one, 16 bars that use all six patterns – jumps to the
arrangement's next bar with that pattern and then walks on through the arrangement, so one cue lasts
a bar or two. The table is in [section 5 of the Unity manual](../../Documentation~/UNITY.md#cueing-patterns).
To hold a pattern whatever the song does, cue it again whenever `music.Bar` changes:
`MusicDirector.HoldPattern` is those five lines. Stop cueing and the arrangement walks on from the bar
it is in, which is how Static Field's hold ends.

### 5. Put it in the scene – [`AudioInstaller.cs`](Scripts/Audio/AudioInstaller.cs)

`AudioInstaller.Install(player, session, song, presetFactory)` creates the whole `Audio` object in plain
runtime code. Call it from your own scene builder, or follow it top to bottom to do the same by hand
in the Inspector:

| Object | Components | Set |
|---|---|---|
| `Music` | `AudioSource`, `SfxMusicPlayer`, your music script | the `SfxSong`; `playOnEnable` |
| `Effects` | `AudioSource`, your one-shot script | the presets to bake |
| `Effects/Footsteps` | `AudioSource` | nothing: a second source for the baked footsteps, because its pitch follows the running speed |
| `Effects/Live Voice 1…3` | `AudioSource`, `SfxPlayer` | no preset: the pool assigns one per trigger |
| `Continuous` | your script that bends the held sounds | the three players below and the MIDI note of each |
| `Continuous/<sound>` | `AudioSource`, `SfxPlayer` | the held sound's preset; `playOnEnable` off |

Every `AudioSource` is 2D, has no clip and has `playOnAwake` off. `SfxPlayer` and `SfxMusicPlayer` add
their sound to the source beside them and keep it running themselves.

### 6. Take the folder with you

Copy `Scripts/Audio`. From `Scripts/Core` it needs these ten small files and nothing else:
`GameEvents`, `PlayerBase` with the three interfaces it implements (`IPlayerState`, `IPlayerActor`,
`IPlayerInput`) and `TerrainPlane`, `GameSessionBase` with `IGameSession`, `GamePhase` and
`SectionId`. Its assembly definition references the assembly `SfxShowcase.Core` by name: point that
at the assembly you copied them into. Then raise the events from your game – or replace the
subscriptions in each `OnEnable` with your own events and the reads of speed, rolling, grounded and
charge (`ContinuousSounds`, `MusicDirector`) with your own values, and drop the Core files altogether.
`ARCHITECTURE.md` section 7 lists exactly what to replace, and the limits (Windows x64, no
spatialisation for live players, what happens without the native library).

## Recording it

The videos and the manual's figures are made from the game itself, without anyone holding a controller.
`Tests/CaptureTakes.cs` holds the takes: each is a Play mode test that plays a scripted piece of the
game and records it. They are marked `[Explicit]`, so the ordinary test run above skips them (its summary line counts them, and the link takes of
`Tests/LinkTakes.cs`, as skipped); you run one by name. A take takes well under a minute.

```sh
UNITY="C:/Program Files/Unity/Hub/Editor/6000.3.8f1/Editor/Unity.exe"   # where your Unity 6000.3 is
PROJECT="$PWD/unity/Demo"                           # run from the repository's root
OUT="$PWD/out"
TAKES=SfxShowcase.Tests.CaptureTakes
record() { "$UNITY" -batchmode -projectPath "$PROJECT" -runTests -testPlatform PlayMode -testFilter "$TAKES.$1" -testResults "$OUT/unity-capture-$1.xml" -logFile "$OUT/unity-capture-$1.log"; grep "CAPTURE take" "$OUT/unity-capture-$1.log"; }

record FullRun          # out/unity-video/full-run: the title card, the whole level, the results (101 s)
record OneShots         # out/unity-video/one-shots: jumps, rows of Chimes with the rising combo, a skid, a Woofer
record HeldSounds       # out/unity-video/held-sounds: the Wind-Up rev, the Burst, the roll hum down a slope and round a loop
record AdaptiveMusic    # out/unity-video/adaptive-music: stand, walk, run, stop, a Burst flat out, stand again
record SectionsAndCues  # out/unity-video/sections-and-cues: Woofer Steps into Static Field, past its Tuning Fork
record HurtAndGoal      # out/unity-video/hurt-and-goal: a hit at a run with twelve Chimes (Split Signal's low terrace), then the goal and the results
record Stills           # out/unity-video/stills: twelve pictures of one run, for the manual
record SyncCheck        # out/unity-video/sync-check: three jumps and three Chimes in silence, to measure with

python docs/video/check_unity_capture.py            # counts, lengths, levels, clipping, and whether sound and picture agree
```

### Recording the link

The link to the device has its own takes. They need the device to be there, so they are explicit too, and end as
"inconclusive" when the two MIDI ports are missing.

1. A virtual MIDI cable with two ports, named `SFX to Unity` and `Unity to SFX` (loopMIDI makes them). Other
   names: set `SFXFORGE_LINK_IN` and `SFXFORGE_LINK_OUT`.
2. The emulator's server: `python .tools/vibe-fm-sdk/tools/emulator.py 8766`.
3. The device's end: `node tests/emulator-link.mjs`. It opens the emulator in a Chrome of its own with a
   throwaway profile, allows that page MIDI, switches SFX FORGE on and puts its MIDI out on `SFX to Unity`.
4. Unity's end, the tests of `Tests/LinkTakes.cs`: `-testFilter SfxShowcase.Tests.LinkTakes`. They ask the device
   for a patch and for the song, play the song that arrives, fetch it twenty times in a row, send a song to the
   device and ask it back (in order, last piece first, after a transfer that broke off), and drive the device.
   Each step that worked logs a line starting with `LINK: ok`. `--spy` on the script logs what MIDI reaches the
   emulator's page and what the page hands to the firmware; `--twice` connects the page's MIDI once more, so the
   firmware gets everything once more.

The recorded session is `Tests/LinkSession.cs`: the game runs at the wall clock's speed, tells the script which
keys to press on the device (through `out/link/cues.txt`), and writes `out/unity-video/link-session/` with a
`link.json` of everything that crossed the ports.

```sh
node tests/emulator-link.mjs --cues out/link/cues.txt --frames out/link/emulator &      # the device, filmed
SFXFORGE_LINK_CUES="$PWD/out/link/cues.txt" "$UNITY" -batchmode -projectPath "$PROJECT" -runTests -testPlatform PlayMode   -testFilter SfxShowcase.Tests.LinkSession -testResults "$OUT/link-session.xml" -logFile "$OUT/link-session.log"
python docs/video/make_link_video.py                # videos/sfx-forge-unity-link.mp4
```

Unity will not open a project twice. With the editor open on `unity/Demo`, run the headless commands on a second
folder that links to the first: a folder with junctions to `Assets`, `Packages` and `ProjectSettings`, its own
`Library`, and beside it a junction named `com.catsplatstudios.sfxforge` to the package.

Do not run it with `-nographics`: the pictures need the graphics card. Several takes in one run:
`-testFilter "$TAKES.OneShots;$TAKES.HeldSounds"`. Exit code 0 means every take in the run recorded
what it was meant to show; a take asserts that (the Woofer fired, the pattern changed) and fails otherwise.

A take's folder holds

| File | What it is |
|---|---|
| `f00000.png`, `f00001.png` … | Every frame, 1920×1080, 30 a second. |
| `audio.wav` | The game's sound for exactly those frames: 48 kHz, 16-bit stereo, recorded at half the listener's volume (see below). |
| `telemetry.json` | For every frame: the player (position, speed, grounded, rolling, charge), the run (phase, section, Chimes), the music (intensity, volume, pattern, bar, step, which of the song's sounds the intensity lets play), the three held sounds (held or let go, and their live values), the live voices. Then two timed lists: every `GameEvents` event, and every SFX FORGE sound it started, with its route (`baked`, `live`, `held`, `music`). The header lists the song's instruments with their layer marks and the notes the director plays by hand. Its `notes` say how the numbers are to be read. |

`stills/` also receives `wind-up.png` and `burst-roll.png` from the take `HeldSounds` and
`hurt-scatter.png` from `HurtAndGoal`. Everything goes to `out/unity-video/` at the repository's root,
which git ignores (in any other project: to `Captures/` in the project's folder); set the environment variable
`SFXFORGE_CAPTURE_DIR` to record somewhere else.
The checker, `docs/unity_figures.py` and `docs/video/make_unity_videos.py` read the same variable.
Recording a take first removes its old pictures and its old `telemetry.json`, so a take that failed
part-way is seen as missing, not as an old one.

How the rig works (`Tests/CaptureRecorder.cs`, about 350 lines; nothing in the game knows about it):

- **The clock.** `Time.captureFramerate = 30`: a frame is 1/30 s of game time however long it takes
  to write. The physics still steps every 0.02 s, as in the tests. The pilot that plays the level
  decides once per physics step (`Tests/CapturePilot.cs`), so the full run is the run the tests check:
  92 seconds, no hit, no respawn.
- **The picture.** The game camera is given a 1920×1080 render texture as its target for the whole
  take and is rendered by hand at the very end of each frame. Because the target is 16:9 all the time,
  the camera's aspect is too, and the view's bounds, the backdrop and the HUD – which lay themselves
  out from the aspect – fill the picture edge to edge. PNGs are compressed on worker threads.
- **The sound.** Real-time audio does not line up with a fixed clock, so nothing is recorded from the
  sound card. `AudioRenderer` takes Unity's audio off the real-time clock; each frame the rig asks it
  for the samples that frame is due and Unity calls SFX FORGE's `OnAudioFilterRead` for them, there and
  then. Unity mixes in blocks of 1024 samples, so a frame gets one or two blocks and the wav is never
  more than one block (21 ms) away from the pictures. Measured with the take `SyncCheck`: a jump's
  baked clip and a Chime's live voice start within 0.7 frames of the frame their event is in.
- **The level.** While the rig is on, `AudioListener.volume` is 0.5 (`CaptureRecorder.ListenerVolume`).
  Unity limits its output to full scale before `AudioRenderer` can read it, so a take recorded at 1
  could never show that the game's mix went over: its largest sample would read exactly 1. At 0.5 the
  mix can be measured: the game, played at full volume, peaks at the take's peak ÷ 0.5, and every take
  asserts that this is under 0.95 (`CaptureRecorder.MixCeiling`). That is how the mix was set. With the
  first volumes the full run reached 1.38 of full scale (rows of Chimes and the Land thump on top of
  the band; a full-charge Burst with the rev, the hum and the wind); the music and most effects were
  turned down (`MusicDirector.musicVolume`, the table in `SoundLibrary.cs`), and the full run now
  peaks at 0.81 to 0.90, depending on the recording. The levels come from these measurements only; nobody has judged the balance by
  listening. The video script brings a take's level back up with one gain.
- **The telemetry** only listens to `GameEvents` and reads public state, like the audio folder. Which
  sound an event starts is worked out with the rules of `SoundEffects` (a soft landing is silent, a
  dense row of Chimes skips pings), read from the component so it follows its Inspector values.
  Those values, the director's cues and phrases, and whether a held sound is held are private; the
  telemetry reads them by reflection and stops with an error if one has been renamed.
- **A cut.** Technique takes move the player with `PlaceAt`, as the tests do, and tell the follow
  camera to be there at once instead of gliding over.

To add a take, copy a short one (`OneShots`): `Rig("name")`, script the input, `Roll()` where the
recording should begin, `Wrap()` at the end.
